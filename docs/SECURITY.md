# Security Model

## Defense in depth

Each layer assumes the one above it may fail.

| Layer | Control |
|---|---|
| Network — internet edge | Only the ALB is internet-facing. Nothing else has a public IP. |
| Network — routing | Data-tier route tables contain only the local VPC route: no NAT, no IGW. The database cannot reach the internet in either direction. |
| Network — segmentation | Security groups chain by reference: internet → ALB SG → ECS SG → RDS SG. No CIDR rules between tiers. |
| Network — AWS APIs | VPC endpoints keep ECR, Secrets Manager, CloudWatch, STS and SSM traffic inside the VPC. |
| Identity | Separate task role and task execution role. GitHub Actions uses OIDC federation; no static keys. |
| Secrets | Passwords generated by Terraform, stored in Secrets Manager, injected at task start, never in env vars or Git. |
| Data at rest | RDS storage encrypted; Terraform state encrypted with a customer-managed KMS key; ECR layers encrypted; ALB logs encrypted. |
| Data in transit | TLS-only bucket policy on state; ALB HTTPS listener with TLS 1.2 minimum when a certificate is supplied. |
| Supply chain | Immutable ECR tags, scan-on-push, pinned providers, committed lock file. |
| Pipeline | Checkov policy scan, `terraform test` assertions, branch protection, environment approvals, plan-file applies. |
| Detection | VPC Flow Logs, ALB access logs, CloudWatch alarms, weekly drift detection. |

## Threat scenarios

**An attacker compromises the application container.**
The task has no public IP and cannot be reached from the internet directly. Its
security group permits inbound traffic only from the ALB. Its task role grants
only what the application needs — not registry or broad secret access, which
belong to the execution role. Lateral movement to the database requires the ECS
security group, which the attacker already has; this is the residual risk that
application-level authentication and least-privilege database grants address.

**An attacker compromises the database.**
The data tier has no route to NAT or the Internet Gateway. Outbound
exfiltration over the network is not possible; data can only leave via a path
that already had legitimate access.

**Credentials leak from the repository.**
There are no AWS credentials in the repository. CI authenticates via OIDC with
credentials that expire at job end. Gitleaks runs as a pre-commit hook, and
`.gitignore` blocks state, tfvars by default, and key material.

**Someone assumes the CI role from another repository.**
The trust policy's `sub` condition restricts assumption to
`repo:<owner>/<repo>` on `main` or a pull request. Without that condition any
GitHub repository could assume the role — it is the single most important line
in the trust policy.

**Terraform state is exfiltrated.**
State contains resource IDs and the generated database password. The bucket
blocks all public access, enforces TLS, is encrypted with a customer-managed
KMS key, and KMS usage is logged in CloudTrail. Compromise still requires valid
IAM credentials with both S3 and KMS access.

## Known gaps

1. The CI role uses `PowerUserAccess` plus a narrow IAM policy — broader than
   true least privilege. Scoping to exact actions and resource ARNs is the next
   hardening step.
2. No automatic secret rotation.
3. No AWS WAF in front of the ALB.
4. No GuardDuty, Security Hub, or AWS Config conformance packs.
5. Single account: environment isolation is logical, not an account boundary.
6. No network ACLs; security groups alone provide segmentation. NACLs would add
   a stateless subnet-level layer.
7. Container runs as a non-root user but with a writable root filesystem.

## Secrets handling rules

Never commit, and never place in `.tfvars`: passwords, API keys, certificates,
private keys, AWS access keys, database connection strings with credentials.

If a secret is ever committed, rotating it is mandatory — removing it from
history is not sufficient, because the value must be assumed compromised the
moment it was pushed.
